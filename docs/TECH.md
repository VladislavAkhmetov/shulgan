# Техническая архитектура (v2.0)

Справочник по тому, как устроен движок «Аманата» сейчас. Геймдизайн — в STORY / LEVELS / COMBAT / COMPANION / EQUIPMENT,
план и статус внедрения — в [ROADMAP.md](./ROADMAP.md).

## Стек

| Слой | Решение |
|---|---|
| Рендер | `three` WebGLRenderer (WebGL2) + собственная постобработка (HDR, маска обзора, bloom, финальный грейдинг) |
| Коллизии и навигация | Поле расстояний (SDF, 0.5 м) из ASCII-карты + аналитические круги + flow field (Dijkstra) |
| Персонажи | GLB со скелетом Mixamo (`hero_rig.glb`, `ubyr_rig.glb`, `wolf_rig.glb`, `marten.glb`); процедурные риги — запасной вариант и для существ без GLB |
| Звук | WebAudio: процедурная музыка (узляу, курай, думбыра) и боевые эффекты + записи CC0 (волки, убыры, лес) |
| UI | React 19 + Tailwind v4 поверх canvas, мост — `core/store.ts` (useSyncExternalStore) |
| Сборка | Vite 8, TypeScript 5.7 |

Принципы: игровой цикл не в React; данные отдельно от кода; без аллокаций в горячем цикле там, где это важно;
отладка с первого дня (`window.__game`, клавиша `` ` `` — FPS / draw calls / треугольники).

## Кадр

Сцена → HDR MSAA-таргет с depth → vision pass (мировая позиция из глубины, маска обзора, туман у земли) →
призрачные силуэты (беркут, сорванная невидимость) → bloom → финальный проход (ACES, сплит-тон, виньетка, зерно, урон/замедление/рассвет).

**Маска обзора** (`render/vision.ts`): каждый кадр ~220 лучей по SDF и кругам-окклюдерам → два веера (конус взгляда и периферия)
в мировую текстуру 4 px/м → временное сглаживание (R — видимо, G — изведано). Конус умножается на освещённость:
«ночное зрение» вокруг героя (`darkFull/darkFade`, зависит от луны и рассвета) и круги света (до 32; `Game.feedVisionLight`).
Свет поясного сосуда Ут-һауыт — круг вокруг Алдара, его радиус уменьшается на 6% за каждую выпитую каплю;
фокус жара [F] добавляет вперёд цепочку кругов конусом до 12 м. `Vision.sees` проверяет то же условие на CPU.

**Освещение:** фиксированное число источников, шейдеры не перекомпилируются: луна с тенью, полусфера, свет сосуда
(`lighting.lantern`, точечный с кубической тенью, привязан к сосуду на кости `Hips`), конус фокуса жара
(`lighting.focus`, SpotLight без тени, постоянно в сцене с нулевой яркостью вне фокуса), пул из 6 точечных без теней для ближайших источников уровня.
Кроны деревьев со стороны камеры срезаются (dither cutaway) в патче материала.

**Бюджет теней:** мелкие детали не отбрасывают тень (`trimShadows`), в тени попадают только крупные объекты
по слоям (`assignShadowLayers`: слой 4 — сосуд, 5 — луна); тень сосуда обновляется через кадр.
Свет сосуда висит на уровне бедра, поэтому от дерева он может показать только тень ствола: в его кубическую тень
деревья попадают как дешёвые шестигранные стволы-заместители (`Batcher.build`, ячейки 12 м, только слой 4), полные деревья
с кронами рисуются лишь в тень луны. Дальность кубической тени — 12 м. Число источников не меняется при [F]:
фокус меняет только интенсивность, поэтому новые варианты шейдеров поверхностей и теней не нужны.
`Game.build` дожидается GLB героя, врагов и спутников, затем `Game.precompile` вызывает `compileAsync`
с привязанным HDR-таргетом сцены и делает один скрытый проход с тенями и временно видимой экипировкой.
Подготовка завершается до начала игры; уничтожение `Game` во время ожидания не возобновляет его цикл.
Замер (04.11.2026), Волчий лог: 638 → 484 вызова, 2,27 → 1,26 млн треугольников
в кадре; сама тень сосуда 248 → 94 вызова, 1,3 млн → 0,29 млн треугольников.

## Уровень

ASCII-карта, клетка 2 м, строка 0 — север. Легенда маркеров — в шапке `level/map.ts`. Зоны (`ZONES`) — прямоугольники
в клетках, название появляется при первом входе. `build.ts` превращает маркеры в объекты и возвращает `LevelBuild`
(капли, тайники со стрелами, капкан, дупло, преграды, триггеры, точки посадки Шурале и т. д.).
Карта и зоны Главы 1 соответствуют LEVELS.md (см. ROADMAP.md, «Глава 1: карта»). Главы 2–3 строятся тем же `buildLevel` с параметром
природы (`biome`: стены — базальт и холмы или известняк и сосульки, пол — ковыль или камень и снег); их маркеры разбирает `extras.ts`.
Глубокая вода `%` непроходима, но прозрачна для взгляда и стрел: у поля есть второе SDF «для глаза» (`Field.see`, `seeClearance`).
Смена главы пересоздаёт `Game` целиком (App.tsx); `hud.reset()` сохраняет настройки игрока.

## Персонажи и экипировка

- **Алдар** (`actors/player.ts`): автомат состояний (move, attack, charge, slam, bash, counter, dodge, hurt, bow, eagle, flash,
  interact, grabbed, finisher, dead). Логический поворот мгновенный, тело доворачивается пружиной.
- **Экипировка** (EQUIPMENT.md) собирается процедурно в `models.ts → createHero` и висит на суставах процедурного скелета;
  `HeroAnimator` переносит каждый предмет на соответствующую кость Mixamo (`mixamorigHips`, `RightHand`, `LeftForeArm`, `Spine2`).
  Когда появятся GLB из ASSETS.md (`eq_*.glb`), меняется только содержимое групп в `createHero`.
  Колчан содержит 8 мешей стрел, видимых по `kit.arrows`. В стойке с луком кылыс уходит в ножны, калкан — за спину.
- **Mixamo-слой героя** (`actors/heroAnim.ts`): клипы из `hero_rig.glb` по именам (`atk_kos`, `atk_obr`, `atk_polu`, `atk_heavy`,
  `block`, `bow_draw`, `bow_aim`, `bow_shot`, `hit`, `throw`, `pickup`, `finisher`, `death`, `stance_*`); недостающие состояния
  берут процедурную позу. Верхний слой (лук, блок) работает поверх ног.
- **Враги** (`actors/enemies.ts`): базовый `Enemy` (восприятие, атаки с окнами урона, стойка, оглушение, метки спутников,
  невидимость, телеграф атак: янтарный блик — можно парировать, красный — неблокируемая).
- **GLB-риги** реализуют интерфейс `Rig` (`root`, `update(dt, {speed, forward, clip, t})`, `hitFlash`, `eyeBoost`, `setLayer`).
  Боевая логика не зависит от того, процедурное тело или GLB.

### Аудит производительности света (05.11.2026)

Разбор кода и замер в браузере на ноутбуке игрока (Intel Iris Xe, выбранная встроенной вкладкой Codex).
Свет, перекрытие обзора и читаемые тени — основа игры. Панель сравнения и исправление первого [F]
реализованы; постоянная просадка на RTX 4050 пока не измерена на самой RTX 4050.

Контекст игрока: GTX 1050 Ti, браузер одновременно с большим числом вкладок, Figma и IDE;
устойчивая заторможенность появляется именно после получения огня. Планируется Steam и увеличение
локации, возможно с делением надвое. Первый A/B-тест — одна точка после получения огня с неизменными
экипировкой и камерой: обычный свет / свет с сохранённой, но не обновляемой картой тени / свет без тени.
Это разделяет стоимость построения карты и её выборки на освещённых пикселях: при нулевой интенсивности
шейдер пропускает выборку point shadow, хотя саму карту наш код продолжает обновлять.
Сравнивать после прогрева вариантов шейдеров, в production-сборке с тем же размером окна;
фоновые приложения — отдельная переменная, а не установленная причина просадки.

Текущий ноутбук — RTX 4050 Laptop; игрок сообщает о просадке и на нём. Для сравнения в своей сцене
открыть панель клавишей `Backquote` (`Ё` / `~`). `4` исключает только щит (в руке и за спиной) из карты
тени сосуда, `5` выключает всю тень сосуда, `6` замораживает её обновление. Свет и маска обзора остаются,
при `4` сохраняются видимый щит и его лунная тень. Повторное нажатие восстанавливает режим.
Замороженная карта годится только для диагностики в одной точке: при движении источника тень неверна.
Сравнивать в качестве `high` спустя 3 с после переключения; первый кадр может компилировать вариант шейдера.
Панель показывает среднее FPS/время за ~0,5 с, p95 последних 120 кадров, число вызовов/треугольников
всего текущего кадра (в том числе проходы обзора и теней), размер буфера и GPU, выбранный браузером.
Время — интервал между requestAnimationFrame, не отдельное GPU-время. HUD обновляется 4 раза в секунду.
Все тестовые переключатели действуют только при открытой панели; закрытие панели и пересоздание игры
восстанавливают обычные настройки теней.
Щит после `trimShadows` имеет примерно три крупных кастера (чаша, обод, орнамент); размер его силуэта
на земле не равен стоимости геометрии. PointLight сейчас поднят на 0,6 м над `vesselCore`.
При UI-проверке встроенная вкладка Codex выбрала Intel Iris Xe (ANGLE/D3D11), несмотря на установленную
RTX 4050 Laptop. Это не измерение GPU, выбранного обычным Chrome со скриншота игрока: его нужно
проверить той же панелью в соответствующем браузере.

#### Исправление первого удержания F

Воспроизводимый прогон: `http://127.0.0.1:8443/tools/focus-benchmark.html` на dev-сервере.
`tools/focus-benchmark.mjs` создаёт отдельный Game, ждёт героя и прогрева, выдаёт уголь, ставит героя
в `(43, 230.6)` у очага и использует реальный RAF и обычный путь клавиатурного ввода. В одной сцене
сравнивает обычный свет, первое/повторное удержание F, выключенный щит, замороженную и отключённую
тень огня. Не меняет сохранённый прогресс. В конце останавливает рендер и печатает JSON в console.
Условие PASS: фокус действительно активен, интенсивность конуса > 50 и новых программ при обоих
удержаниях нет. Для проверки запускать в отдельной вкладке; это не software/headless GL.

Обнаружены три причины компиляции во время игры: скрытие SpotLight меняло ключи шейдеров (в том числе
`depth`/`distance`), ранний прогрев не охватывал поздние GLB, а `compile()` для экранного буфера
готовил sRGB-варианты вместо реально используемых HDR-вариантов. Обычный `compileAsync` также
не готовит материалы внутренних теневых проходов — для них добавлен скрытый проход до начала игры.

Замер 05.11.2026, ANGLE/D3D11 Intel Iris Xe, буфер 1920×1080 (DPR 1.5):

| Первое удержание F | До исправления | После |
|---|---:|---:|
| Новых шейдерных программ | 28 | 0 |
| Самый долгий интервал между кадрами | 2066.7 мс | 50.3 мс |
| Максимальное CPU-время кадра (JS + вызовы драйвера) | 2063.5 мс | 28.7 мс |

Это устранение разового фриза, не доказательство 60 FPS на RTX 4050: p50 обычной сцены и первого F
остался ~33.3 мс, p95 ~50 мс. Выключение щита в этой точке заметного улучшения этих интервалов
не дало. Отдельное GPU-время не измерялось; нельзя приписывать всю постоянную нагрузку щиту.

- В `package.json` и локальном `node_modules` уже `three` 0.187.0. Рендер остаётся `WebGLRenderer`:
  наличие r187 само по себе не включает WebGPU или clustered lighting.
- Луна: карта 2048², область 48×48 м, обновление каждый кадр. Сосуд: шесть граней 512²,
  обновление через кадр (каждый кадр при high и FPS > 100). Проверить время обоих типов кадров:
  усреднённый FPS скрывает чередование тяжёлого и лёгкого кадра. Обновление тени сосуда сейчас
  запрашивается и при погашенном свете; его следует пропускать, сохранив обновление при включении.
- HDR-таргет: MSAA 4×; DPR до 1.5; полноэкранная маска обзора с процедурным туманом, bloom и грейдинг.
  DPR 1.5 даёт в 2.25 раза больше пикселей, чем DPR 1 при том же размере окна.
- Исправлен отладочный HUD: `info.autoReset = false`, сброс перед обновлением/отрисовкой кадра;
  раньше счётчики сбрасывались при каждом `render()` и показывали только финальный проход.

Порядок проверки:

1. Считать draw calls/треугольники за весь кадр (`info.autoReset = false`, сброс перед GPU-проходами,
   включая `Vision.update`), время CPU отдельно от асинхронных GPU timer queries, если они доступны;
   сохранять медиану и p95 времени кадра. Сравнить одинаковый маршрут после прогрева ассетов и шейдеров.
   Отдельные диагностические переключатели: лунная тень, тень сосуда, туман, bloom, DPR и MSAA.
   Тестировать бой, густой лес и главы 2–3; headless/software GL не считать замером целевого железа.
2. Сначала уменьшать стоимость одного обновления тени: распространить shadow proxy на кроны и камни,
   проверить размеры spatial chunks (сейчас основные инстансы — 40 м, стволы-заместители — 12 м),
   отсечение кастеров и пропуск обновлений погашенного сосуда. Частоту теней менять по результатам замеров.
3. Проверить DPR/render scale с сохранением разрешения HUD, MSAA 2× против 4×, более дешёвый шум тумана
   и разрешение bloom. Пресет `low` сейчас отключает тень сосуда: нужен эксперимент с доступным режимом,
   который сохраняет ближние тени. Перепады яркости, колебание света на кости и дрожание границ теней
   оценивать отдельно от FPS.
4. Для нового окружения готовить LOD, shadow proxy, общие материалы, instancing/batching и KTX2-текстуры;
   для персонажей — ограничивать число мешей/материалов и частоту анимации удалённых существ.
   Процедурная болванка из многих мешей может стоить дороже подготовленного GLB. Бюджет кадра должен
   оставлять резерв для окончательных ассетов, а не только укладываться в лимит на текущем прототипе.
5. Затем оценить гибрид: статическое окружение — запечённое освещение/AO и/или кэш лунных теней,
   персонажи и ближний огонь — динамические тени. Кэширование требует отдельного решения для движущихся
   кастеров, ветра, слежения лунной камеры и изменений окружения; просто заморозить общую карту нельзя.

Увеличение карты: подгружать/активировать пространственные участки с учётом камеры и источников теней,
а не держать весь новый контент активным. Деление главы уменьшает загрузку и расход памяти, но само
по себе не удешевляет локальный свет в прежнем кадре. Упаковка для Steam также не заменяет оптимизацию
рендера; финальный профиль проверять в выбранной оболочке на целевом компьютере.

WebGPU/TSL — отдельный прототип с тем же маршрутом и сравнением кадра. Наши `ShaderMaterial`,
`onBeforeCompile` (ветер, cutaway, rim) и `UnrealBloomPass` требуют переноса на совместимые узлы/проходы.
В r187 интересны [ClusteredLighting](https://github.com/mrdoob/three.js/pull/34978) (много point/spot lights;
WebGL2 fallback относится к `WebGPURenderer`, не к нашему `WebGLRenderer`) и
[LightMapper](https://github.com/mrdoob/three.js/blob/r187/examples/jsm/lighting/LightMapper.js)
(запекание diffuse irradiance, нужны UV и `WebGPURenderer`). Они не устраняют стоимость шести граней
динамической тени сосуда. Исправление швов point shadows в r187 — исправление изображения,
а не обещание роста FPS. Источники: [релиз r187](https://github.com/mrdoob/three.js/releases/tag/r187),
[руководство WebGPU](https://threejs.org/manual/pages/webgpurenderer).

## Правила интерфейса

- HUD в углах, из линий: здоровье и Запал внизу слева, стойки, колчан, сосуд и беркут внизу справа, босс — внизу по центру.
  Вне опасности HUD растворяется.
- Шрифты: **Forum** (заголовки, имена), **Alegreya** (речь, курсив), **Alegreya Sans** (служебное, клавиши).
- Цвета: кость `#d9d2c3`, янтарь `#e89b3c` (фокус, действие, жар сосуда), охра `#a4452c` (раны, печати),
  серебро `#b8e8ff` только для живой воды (LEVELS.md, ASSETS.md 2.4).
- Иконки — только собственные знаки `src/ui/glyphs.tsx`. Без рамок, карточек и уголков-орнаментов.
- Подсказка клавиши пишется в тексте как `[E]` и рисуется клавишей. Каждый экран управляется с клавиатуры и мыши.
- Онбординг (`tutor.ts`): один шаг на экране, засчитывается действием, опасность встаёт перед текущим уроком.
- Тексты короткие, без современной лексики (DIALOGUES.md).

## Видеофон главного меню (06.11.2026)

`src/ui/MenuBackdrop.tsx` монтируется только внутри титульного `Title` в `Screens.tsx`.
`public/video/menu-lake-moon-trimmed.mp4` (1918×1080, 11.50 с) проигрывается с `playbackRate = 0.6`
и `defaultPlaybackRate = 0.6`, поэтому цикл длится около 19.17 с. Выбрана обрезка предыдущего ролика:
кадры 6–281 при 24 fps, [0.25, 11.75) с. В файле сохранена исходная скорость; замедление только в плеере.
Постер `menu-lake-moon-trimmed.webp` взят из нового первого кадра. Оригинал и прежний постер сохранены
в `assets-src/cinematics/menu/original/`; новые URL исключают старую версию из браузерного кэша.
Видео использует `autoPlay`, `loop`, `muted`, `playsInline`, `object-cover`; под ним всегда есть
WebP-постер из первого кадра. Плавное появление начинается по `playing`, при ошибке остаётся постер.
`prefers-reduced-motion: reduce` отключает видео; изменение настройки учитывается без перезагрузки.
`visibilitychange` приостанавливает видео и возобновляет его при возврате; размонтирование удаляет
источник и вызывает `load()` для освобождения декодера. На странице управления фон дополнительно затемнён.

Игровой цикл на титуле продолжает опрашивать ввод и ждать готовность уровня, но пропускает
`update` / `idle` и `render`: иначе скрытая `Vision.update` всё ещё выполняет проходы WebGL.
После ухода с титула обычные обновления и рендер возобновляются. Построение и прогрев сцены не изменены.
Браузерная проверка production-сборки подтвердила 0 вызовов `renderer.render` на готовом титуле,
повтор видео, запасной постер, управление и переход в игру без ошибок JavaScript.

## Тесты

- `pnpm check:chapter1` (`tools/check-chapter1.mts`): Node сам убирает типы из `level/map.ts`; проверяет маркеры, проходимость
  BFS по сетке (оба пути на север, закрытость без них), досягаемость ключевых мест и покрытие зон.
- `pnpm check:chapters` (`tools/check-chapters.mts`): то же для карт глав 2–3, с непроходимой глубокой водой, завесой и мостком.
- `pnpm playtest:chapter1|2|3 [url]` (`tools/playtest-chapter*.mjs`, общий `tools/playtest-harness.mjs`): Chromium с программным GL,
  протокол DevTools; главы 2–3 открываются через `#chapter=N`. Обёртка `chromium` сразу завершается, поэтому харнесс держит цикл
  событий таймером и закрывает браузер по порту отладки; после сборки уровня он ждёт 12 с, пока догрузятся модели. Игровой цикл
  останавливается, симуляция двигается вручную по 1/30 с (`Game.update` без отрисовки), ввод — синтетические события
  клавиатуры и мыши, прицел задаётся тестом. Каждый шаг возвращает `true` или причину; ошибки страницы — провал.
  Кадры для визуальной проверки снимаются так же, вызывая `Game.render` перед `Page.captureScreenshot`.
